# Exam Format and Syllabus

## Exam Format

| **Parameter**              | **Value**                                                 |
| -------------------------- | --------------------------------------------------------- |
| **Question type**          | Multiple choice — **1 correct answer out of 4 options**   |
| **Total questions**        | **60**                                                    |
| **Scoring**                | **100–1000 scale**                                        |
| **Passing score**          | **720 / 1000**                                            |
| **Guessing penalty**       | **None** — answer every question                          |
| **Scenarios**              | **4 out of 8 possible scenarios**, randomly selected      |
| **Questions per scenario** | Multiple questions may be based on each selected scenario |
| **Nature of questions**    | **Scenario-based / application-oriented**                 |

## Syllabus and Key Considerations

| **[Domain](ca://s?q=Claude_Architect_exam_domains)** | **Exam Weight** | **[What’s Tested](ca://s?q=Claude_Architect_exam_topics)** | **[Question Style](ca://s?q=Claude_Architect_exam_question_style)** | **[Common Failure Point](ca://s?q=Claude_Architect_exam_failure_points)** |
| --- | --- | --- | --- | --- |
| **Agentic Architecture & Orchestration** | 27% | - Distinguish **agent vs workflow vs conversational system**.<br>- Apply **task decomposition** (atomic vs composite tasks).<br>- Choose **sequential vs parallel execution**.<br>- Design **orchestrator–subagent patterns** (hub‑and‑spoke, DAG).<br>- Balance autonomy vs reliability. | **Scenario‑based**: Given a complex task (e.g., “Summarize portfolio, compare to benchmark, draft email”), select the correct architecture and justify why it’s optimal.<br>Expect diagrams, dependency graphs, or pseudo‑code snippets. | - Defaulting to “just add an agent” when a **simpler workflow** (e.g., sequential API calls) would be more reliable.<br>- Confusing **conversation loops** with **execution loops**.<br>- Over‑engineering orchestration (too many agents, no dependency awareness). |
| **Multi-Agent Topologies** *(sub-area within above)* | — | Hub-and-spoke, pipeline, and peer-to-peer patterns; context isolation between agents; handoff design | Scenario: match topology to failure-containment and coordination needs | Treating topologies as interchangeable instead of structural commitments |
| **Tool Design & MCP Integration** | 18% | Schema design, tool legibility to the model, MCP server integration patterns | Scenario: debug or improve a poorly-designed tool interface | Optimizing schema validity while ignoring model-side comprehension |
| **Claude Code Configuration & Workflows** | 20% | Configuration, deployment patterns, CI/CD integration for Claude-based systems | Applied/config-based scenarios | Confusing local dev setup habits with production-grade workflow design |
| **Prompt Engineering & Structured Output** | 20% | Structured output design, prompt reliability, output contracts | Scenario: fix or design a prompt for consistent structured results | Treating prompts as instructions rather than as reliability contracts |
| **Context Management & Reliability** | 15% | Session/state handling, retrieval strategy, summarization, what to retain vs. discard | Scenario: system degrades under long context — diagnose and fix | Treating context loss as a bug rather than an architectural decision point |

**On exam mechanics to keep in mind while studying:**
- Closed-book, proctored, no AI assistance — recall alone won't carry you through scenario items.
- The exam rewards *tradeoff reasoning*: most scenario questions have more than one technically valid answer, and the correct choice depends on constraints stated in the scenario (latency, cost, failure tolerance, team maturity).
- Expect "which of these is the best next step" framing more than "which of these is true" framing.
