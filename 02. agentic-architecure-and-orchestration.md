# Multi-Agent Orchestration – Detailed Notes

## What It Is
- **Definition:** Coordinating multiple AI agents (or tool chains) to solve complex tasks.  
- **Purpose:** Break down large workflows into specialized roles, then merge results.  
- **Architect’s Role:** Design **roles, routing, stop control, error handling, and context management**.


The orchestrator (sometimes called the supervisor, planner, or coordinator) is responsible for:
- Breaking a task into subtasks
- Selecting the appropriate agent
- Passing context between agents
- Managing execution order
- Handling failures
- Combining results
- Returning a final response

The orchestrator itself may be an LLM or traditional application logic.

## Multi-Agent Orchestration – Critical Points & Core Principles

## Agent Specialization
- Each agent is designed for a **specific domain**.  
- Example roles:  
  - **Validator Agent** → checks customer data.  
  - **Summarizer Agent** → condenses long text.  
  - **Creative Agent** → generates narratives or marketing copy.  
- **Architect Insight:** Specialization prevents agents from becoming “generalists” that waste tokens or produce inconsistent results.

## Message Routing
- Subagents **never talk directly**.  
- Coordinator routes outputs into the `messages` array for the next agent.  
- Example:  
  - Validator result → passed to Summarizer.  
  - Summarizer output → passed to Report Generator.  
- **Architect Insight:** Routing ensures controlled communication and avoids chaos.

## Stop Control
- Use markers like `stop_sequence`, `end_turn`, or `pause_turn` to segment outputs.  
- Example:  
  - Agent 1 ends with `end_turn` → Coordinator knows to pass result to Agent 2.  
- **Architect Insight:** Stop control prevents agents from running indefinitely or overlapping.

## Parallel Execution
- Independent agents can run **simultaneously**.  
- Example:  
  - Weather Agent checks Austin forecast.  
  - Validator Agent checks customer status.  
- Coordinator merges results.  
- **Architect Insight:** Parallelism saves time but requires careful merging logic.


## Error Isolation
- If one agent fails, Coordinator logs error and continues.  
- Example:  
  - Weather Agent fails → Coordinator still delivers Validator + Report outputs.  
- **Architect Insight:** Isolation ensures resilience; one failure doesn’t collapse the workflow.


## Context Management
- Summarize or chunk outputs to avoid `model_context_window_exceeded`.  
- Example:  
  - Replace 20 long turns with: *“Summary: Customer validated, weather checked, compliance drafted.”*  
- **Architect Insight:** Context trimming keeps orchestration scalable and prevents overflow.

## Architect-Level Strategies

- **Sequential Orchestration:**  
  Agent A → Agent B → Agent C. Each depends on the previous.  
  *Example:* Validator → Summarizer → Report Generator.  

- **Parallel Orchestration:**  
  Agents run at the same time, results merged.  
  *Example:* Weather Agent + Customer Agent → Combined synthesis.  

- **Hybrid Orchestration:**  
  Mix of sequential and parallel.  
  *Example:* Validator + Weather (parallel) → Report Generator (sequential).  

- **Hierarchical Orchestration:**  
  Supervisory agent delegates tasks to sub-agents, then integrates results.  

- **Dynamic Orchestration:**  
  The orchestrator does not follow a fixed workflow. Instead, it decides the next agent, tool, or action at runtime based on intermediate results, user input, or changing conditions. This enables adaptive and autonomous problem solving.  
  *Example:* Planner → Research Agent → (Finds missing data) → Database Agent → Analyst Agent → Report Generator.

- **Debate Orchestration:**  
  Two or more agents independently solve or analyze the same problem from different perspectives. A judge or supervisor agent evaluates their responses, resolves disagreements, and selects or synthesizes the best final answer. This pattern improves reasoning quality and reduces hallucinations.  
  *Example:* Analyst A + Analyst B → Judge Agent → Final Recommendation.

| Pattern      | Flow                    | Advantages            | Disadvantages      | Best Use           |
| ------------ | ----------------------- | --------------------- | ------------------ | ------------------ |
| Sequential   | A → B → C               | Simple, deterministic | Slow               | Pipelines          |
| Parallel     | A + B                   | Fast                  | Merge complexity   | Independent tasks  |
| Hybrid       | (A+B) → C               | Balanced              | More orchestration | Enterprise systems |
| Hierarchical | Supervisor → Workers    | Scalable              | Higher overhead    | Large systems      |
| Dynamic      | Planner decides         | Flexible              | Harder to debug    | Autonomous agents  |
| Debate       | Multiple agents → Judge | Higher accuracy       | Expensive          | Critical reasoning |

##  Coordinator Responsibilities

### Core Responsibilities

- **Task Decomposition:**  
  Break down a large, complex request into smaller subtasks.  
  *Example:* “Generate compliance report” → (1) Validate customer, (2) Check regulations, (3) Draft report.

  One of the biggest risks in multi-agent orchestration is overly narrow decomposition. This happens when the coordinator breaks a broad task into subtasks but misses important dimensions. For example, if the query is “Research creative industries” and the coordinator only decomposes it into visual arts, the orchestration will fail to cover music, writing, film, and design. The result is incomplete synthesis, which the exam specifically tests for.

  The fix is to design broader initial decomposition. The coordinator should start by mapping the full scope of the query, identifying all relevant domains, and explicitly checking for coverage. In the creative industries example, this means ensuring the subtasks include visual arts, performing arts, literature, film, and design. By doing this, the coordinator avoids blind spots and ensures the final synthesis is comprehensive.

  Architects also use coverage checks to validate decomposition. After subtasks are defined, the coordinator evaluates whether each major domain of the query is represented. If gaps exist, it re-delegates to additional subagents. This prevents narrow decomposition from undermining the quality of the final output. In short, the coordinator must balance precision with breadth: subtasks should be specific enough to be actionable, but broad enough to capture the full scope of the user’s request.


- **Dynamic Orchestration:** The orchestrator does not follow a fixed workflow. Instead, it decides the next agent, tool, or action at runtime based on intermediate results, user input, or changing conditions. This enables adaptive and autonomous problem solving. Example: Planner → Research Agent → (Finds missing data) → Database Agent → Analyst Agent → Report Generator.
  Dynamic Subagent Selection is about making orchestration smarter and more efficient. Instead of blindly running every agent in a pipeline, the coordinator first looks at the user’s query and decides which agents are actually needed. This prevents wasted computation, reduces token usage, and avoids unnecessary complexity. In practice, it means the system doesn’t always trigger validation, summarization, analysis, and synthesis if the query can be answered by a single specialized agent.
  For example, if a user asks a straightforward factual question like “What’s the weather in Austin today?”, the coordinator should only invoke the Weather Agent. It doesn’t need to involve a Summarizer Agent or a Creative Agent, because the query is simple. On the other hand, if the user asks for a compliance report that requires multiple checks, the coordinator will dynamically select the Validator Agent, the Analyst Agent, and then the Report Agent to combine their outputs. This flexibility ensures that the orchestration adapts to the complexity of the task.
  
  The key benefit is efficiency. By only invoking relevant subagents, the coordinator keeps the workflow lean, avoids hitting the model context window, and reduces the risk of errors cascading across agents. It also improves quality, because the final output is focused on what the user actually asked for, rather than bloated with unnecessary steps. In short, Dynamic Subagent Selection = smart orchestration: the coordinator assesses the query, picks only what’s needed, and skips the rest.

- **Delegation to Subagents:**  
  Assign each subtask to the most appropriate specialized agent.  
  *Example:* Validator Agent handles customer checks, Summarizer Agent condenses findings.  

- **Routing Communication:**  
  Subagents never talk directly. Coordinator passes outputs between them.  
  *Example:* Validator’s result → routed to Summarizer → routed to Report Generator.  

- **Aggregation of Results:**  
  Collect outputs from all subagents and merge into a coherent final answer.  
  *Example:* Combine validation + weather + compliance into one structured report.  

- **Error Handling:**  
  Detect failures (e.g., tool error, refusal) and decide whether to retry, skip, or reassign.  
  *Example:* If Weather Agent fails, Coordinator logs error and continues with other agents.  

- **Quality Evaluation:**  
  Assess synthesis quality. If gaps exist, re-delegate tasks to fill them.  
  *Example:* If report lacks citations, Coordinator reassigns Summarizer Agent to add references.  

- **Iterative Refinement:** Iterative refinement loops are a strategy the coordinator uses to ensure that the final synthesis is complete and high quality. Instead of assuming the first round of subagent outputs will be perfect, the coordinator evaluates the results, identifies gaps, and then re-delegates tasks in a second round. This creates a feedback cycle where the system progressively improves the output until it meets the required standard. 
 The process typically looks like this: in Round 1, the coordinator delegates subtasks to relevant subagents (e.g., Validator, Summarizer, Analyst). Once their outputs are returned, the coordinator performs a quality check. If the synthesis is missing coverage, lacks depth, or contains errors, the coordinator explicitly identifies those gaps. In Round 2, the coordinator reassigns targeted subtasks to fill those gaps — for example, asking the Summarizer to expand on missing domains or the Analyst to add citations. Finally, the coordinator aggregates the refined outputs into a final synthesis. 
 This loop is critical because it prevents incomplete or shallow answers. Without iterative refinement, orchestration risks producing outputs that look polished but fail to cover the full scope of the query. By embedding evaluation and re-delegation into the workflow, the coordinator ensures that the system adapts dynamically to gaps and produces a comprehensive, reliable result. In short, iterative refinement loops = quality assurance in orchestration: evaluate, identify gaps, and refine until the synthesis is complete.

```
      │

Identify Gaps

      ▼
```

## Functional Logic : Core Banking - Sequential Orchestration

```python
from anthropic import Anthropic
import logging
import time

client = Anthropic()

class Coordinator:
    def __init__(self):
        self.messages = []
        self.results = {}
        logging.basicConfig(level=logging.INFO)

    def call_agent(self, prompt, max_tokens=500, retries=3):
        """Generic agent call with retry + logging"""
        for attempt in range(retries):
            try:
                self.messages.append({"role": "user", "content": prompt})
                response = client.messages.create(
                    model="claude-3-opus-20240229",
                    max_tokens=max_tokens,
                    messages=self.messages
                )
                self.messages.append({"role": "assistant", "content": response.content})
                logging.info(f"Agent success: {prompt}")
                return response.content
            except Exception as e:
                logging.error(f"Agent failed: {prompt}, attempt {attempt+1}, error={e}")
                time.sleep(2 ** attempt)  # exponential backoff
        return None  # fail gracefully

    def run_workflow(self, customer_id):
        # Step 1: Validator Agent
        self.results["validation"] = self.call_agent(
            f"Validate customer {customer_id} for KYC."
        )

        # Step 2: Credit Checker Agent
        self.results["credit"] = self.call_agent(
            f"Check credit score for {customer_id}."
        )

        # Step 3: Risk Analyst Agent
        self.results["risk"] = self.call_agent(
            "Perform risk analysis using validation + credit results."
        )

        # Step 4: Compliance Reporter Agent
        self.results["report"] = self.call_agent(
            "Generate compliance report based on validation, credit, and risk analysis.",
            max_tokens=1000
        )

        return self.results["report"]
```

- **Error Isolation** → failures don’t crash the workflow.  
- **Coordinator Control** → manages sequence, routing, aggregation.  
- **Scalability Hooks** → can be extended with queues or parallel execution.  
- **Compliance Awareness** → final report integrates validation, credit, and risk.

```python
from anthropic import Anthropic

client = Anthropic()

class Coordinator:
    def __init__(self):
        self.messages = []
        self.results = {}

    def call_agent(self, prompt, max_tokens=500):
        self.messages.append({"role": "user", "content": prompt})
        response = client.messages.create(
            model="claude-3-opus-20240229",
            max_tokens=max_tokens,
            messages=self.messages
        )
        self.messages.append({"role": "assistant", "content": response.content})
        return response.content

    def run_parallel_workflow(self, customer_id):
        # Step 1: Run Fraud Check + Credit Check in parallel
        with concurrent.futures.ThreadPoolExecutor() as executor:
            fraud_future = executor.submit(
                self.call_agent, f"Run fraud check for {customer_id}."
            )
            credit_future = executor.submit(
                self.call_agent, f"Check credit score for {customer_id}."
            )

            self.results["fraud"] = fraud_future.result()
            self.results["credit"] = credit_future.result()

        # Step 2: Risk Analysis (depends on fraud + credit)
        self.results["risk"] = self.call_agent(
            "Perform risk analysis using fraud + credit results."
        )

        # Step 3: Compliance Report
        self.results["report"] = self.call_agent(
            "Generate compliance report based on fraud, credit, and risk analysis.",
            max_tokens=1000
        )

        return self.results["report"]
```

```python
        # Step 5: Always run Compliance Reporter
```

When you introduce a **Judge agent** into a multi‑agent orchestration, you’re essentially adding a **meta‑agent** whose job is to evaluate the outputs of other agents, resolve conflicts, and ensure quality before the coordinator synthesizes the final answer.  


## Multi‑Agent Orchestration with Judge

### Core Role of the Judge
- **Evaluation** → checks correctness, completeness, and consistency of subagent outputs.  
- **Conflict Resolution** → decides between contradictory outputs (e.g., two risk models disagree).  
- **Quality Assurance** → ensures compliance, accuracy, and regulatory standards.  
- **Feedback Loop** → sends refinement requests back to subagents if gaps are found.  


### Example Flow (Core Banking Loan Workflow)
1. **Validator Agent** → verifies customer identity.  
2. **Credit Checker Agent** → retrieves credit score.  
3. **Fraud Agent** → runs fraud detection.  
4. **Risk Analyst Agent** → evaluates eligibility.  
5. **Judge Agent** → reviews all outputs:  
   - Confirms validation matches fraud check.  
   - Confirms credit score is consistent with risk analysis.  
   - Flags contradictions or missing data.  
6. **Compliance Reporter Agent** → generates final report using Judge‑approved outputs.

```python
        # Simple evaluation logic

        self.results["risk"] = self.call_agent("Perform risk analysis using validation + credit + fraud results.")

        # Judge agent evaluates
        judge = JudgeAgent(self)
        evaluation = judge.evaluate(self.results)

        if evaluation["status"] != "approved":
            return f"Workflow incomplete. Issues: {evaluation['issues']}"

        # Compliance report only if Judge approves
        self.results["report"] = self.call_agent(
            "Generate compliance report based on validated, judged results.",
            max_tokens=1000
        )
        return self.results["report"]
```

```
    ├── Fraud Check
    └── Risk Analyst
         │
         ▼
       Judge Agent ──► Compliance Reporter
                          │
                          ▼
                     Final Report
```

✅ In short: The **Judge agent** acts as the **arbiter** — it reviews, validates, and resolves conflicts among multiple agents before the coordinator allows synthesis. This ensures **quality assurance** in multi‑agent orchestration.

## Section Notes: Passing Context Between Agents

### Shared State
- Use a central dictionary (`results`) to store outputs.  
- Each agent writes its result into `results["agent_name"]`.  
- Subsequent agents read from this dictionary.  

```
self.results["validation"] = self.call_agent(f"Validate customer {customer_id} for KYC.")
self.results["credit"] = self.call_agent(f"Check credit score for {customer_id}.")
# Later agents read from self.results
risk_prompt = f"Perform risk analysis using validation={self.results['validation']} and credit={self.results['credit']}."
self.results["risk"] = self.call_agent(risk_prompt)
```

### Message History
- Append outputs into the `messages` array so Claude sees prior context.  
- Ensures conversational continuity across agents.  
- Risk: context window overflow → mitigate with summarization.  

```
self.messages.append({"role": "user", "content": "Validate customer CUST12345 for KYC."})
response = client.messages.create(model="claude-3-opus-20240229", messages=self.messages)
self.messages.append({"role": "assistant", "content": response.content})
```

### Context Flags
- Boolean switches (`validated`, `fraud_risk`, `credit_cached`) guide dynamic orchestration.  
- Coordinator decides whether to skip or run agents based on flags.  
- Example: `if not context_flags.get("validated") → run Validator`.  

```
context_flags = {"validated": True, "credit_cached": False, "fraud_risk": True}

if not context_flags.get("validated"):
    self.results["validation"] = self.call_agent("Run KYC validation.")
if not context_flags.get("credit_cached"):
    self.results["credit"] = self.call_agent("Check credit score.")
```

### Selective Passing
- Don’t dump entire outputs into every agent.  
- Pass only relevant slices (e.g., credit score, fraud status).  
- Summarize long outputs before forwarding.  

```
credit_score = self.results["credit"].split()[0]  # extract numeric score
risk_prompt = f"Perform risk analysis using credit score={credit_score}."
self.results["risk"] = self.call_agent(risk_prompt)
```

### Aggregation
- Final agents (Risk Analyst, Compliance Reporter) consume multiple prior results.  
- Coordinator merges context into a single prompt.  
- Example: `"Perform risk analysis using validation={...}, credit={...}, fraud={...}"`.  

```
report_prompt = (
    f"Generate compliance report using validation={self.results['validation']}, "
    f"fraud={self.results['fraud']}, credit={self.results['credit']}, "
    f"risk={self.results['risk']}."
)
self.results["report"] = self.call_agent(report_prompt, max_tokens=1000)
```

### Error Handling
- If context is missing (e.g., no credit score), coordinator logs issue.  
- Judge agent can evaluate completeness before compliance synthesis.  
- Prevents incomplete workflows from producing false approvals.  

```
if not self.results.get("credit"):
    logging.error("Credit check missing, cannot proceed to risk analysis.")
    return "Workflow failed: missing credit score."
```

✅ In short: **Context flows through shared state + message history, guided by flags, selectively passed, aggregated at the end, and validated by error handling or judge agents.**  



## **Claude Code vs Claude Agent SDK**

### Claude Code
- **Purpose** → A coding‑focused interface for Claude.  
- **Usage** → You send Claude programming tasks (e.g., “review this Python function”, “generate TypeScript tests”).  
- **Style** → It’s essentially Claude acting as a **code assistant** inside the Anthropic API.  
- **Control** → You call `client.messages.create` directly, pass in your code as input, and Claude responds with analysis, fixes, or generated code.  
- **Agentic behavior** → Minimal. It’s just Claude generating text/code — you handle everything else.


### Claude Agent SDK
- **Purpose** → A higher‑level orchestration framework for building **agentic workflows**.  
- **Usage** → You import helpers like **query**, **ClaudeAgentOptions**, and **AgentDefinition**.  
- **Style** → You define **tools** and **agents** (specialized roles like “code‑reviewer” or “test‑writer”). Claude can spawn and coordinate them.  
- **Control** → The SDK manages the agent loop, tool calls, and streaming output. You don’t manually handle `stop_reason`.  
- **Agentic behavior** → Strong. Claude decides which agent/tool to use, and the SDK routes execution to your Python functions.


### Side‑by‑Side Comparison

| Feature | **Claude Code** | **Claude Agent SDK** |
|---------|-----------------|-----------------------|
| Focus | Code generation & review | Multi‑agent orchestration |
| API Call | `client.messages.create` | `query(prompt, options)` |
| Tools | None by default | Register tools (`validate_customer`, `check_credit`) |
| Agents | Single Claude instance | Multiple specialized agents (`code-reviewer`, `test-writer`) |
| Control | You handle stop reasons | SDK abstracts stop reasons |
| Streaming | Manual (`client.messages.stream`) | Built‑in async generator (`async for message in query(...)`) |


### Key Takeaway
- **Claude Code** → Think “Claude as a coding copilot.” Direct API calls, focused on programming tasks.  
- **Claude Agent SDK** → Think “Claude as an orchestrator.” You define agents and tools, SDK manages agentic workflows.  


✅ So: Claude Code is a *mode of use* (code assistant), while the Agent SDK is a *framework* for agentic orchestration. Both use the same Anthropic API under the hood, but at different abstraction levels.  


## Difference Between the Two Styles of Agentic Coding

### 1. **Raw Agentic Loop (Anthropic SDK)**
```python
# Install first:
#   pip install anthropic

import anthropic

client = anthropic.Anthropic()

# Step 1: Define the tool
tools = [
    {
        "name": "validate_customer",
        "description": "Validate customer account and KYC status",
        "input_schema": {
            "type": "object",
            "properties": {
                "customer_id": {"type": "string"},
                "account_number": {"type": "string"}
            },
            "required": ["customer_id", "account_number"],
        },
    }
]

# Step 2: Implement the actual method
def execute_tool(name, tool_input):
    if name == "validate_customer":
        if tool_input["customer_id"] == "CUST123" and tool_input["account_number"] == "ACC456":
            return "Customer is valid: KYC complete, account active, no fraud flags."
        else:
            return "Customer validation failed: account inactive or KYC pending."
    return "Unknown tool"

# Step 3: Start conversation
messages = [{"role": "user", "content": "Validate customer CUST123 with account ACC456"}]

# Step 4: Agentic execution loop
while True:
    response = client.messages.create(
        model="claude-sonnet-5",
        max_tokens=1024,
        tools=tools,
        messages=messages,
    )

    # Append Claude’s response to history
    messages.append({"role": "assistant", "content": response.content})

    match response.stop_reason:

        case "tool_use":
            tool_results = []
            for block in response.content:
                if block.type == "tool_use":
                    result = execute_tool(block.name, block.input)
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": result,
                    })
            # Feed tool results back to Claude
            messages.append({"role": "user", "content": tool_results})
            continue

        case "pause_turn":
            continue

        case "end_turn" | "stop_sequence":
            final_text = "".join(b.text for b in response.content if b.type == "text")
            print("Final Output:", final_text)
            break

        case "max_tokens":
            print("Truncated — consider raising max_tokens or summarizing history.")
            break

        case "refusal":
            print("Refused:", response.stop_reason, getattr(response, "stop_details", None))
            messages = messages[:1]  # reset conversation
            break

        case "model_context_window_exceeded":
            print("Hit context window — trim or summarize `messages` and retry.")
            break

```
- This is the **low‑level agentic code**.  
- You directly call `client.messages.create`.  
- You manually handle `stop_reason` (`tool_use`, `end_turn`, etc.).  
- You define tools and execute them yourself (`execute_tool`).  
- This gives you **full control** over the agent loop.


### 2. **High‑Level Orchestration (Claude Agent SDK)**

```python
# Install first:
#   pip install claude-agent-sdk anthropic

# Step 1: Define your tool logic (the "actual method")
def validate_customer(customer_id: str, account_number: str) -> str:
    if customer_id == "CUST123" and account_number == "ACC456":
        return "Customer is valid: KYC complete, account active, no fraud flags."
    else:
        return "Customer validation failed: account inactive or KYC pending."

# Step 2: Register tool in context
options = ClaudeAgentOptions(
    allowedTools=["Agent"],   # allow Claude to spawn subagents
    context={
        "customer_id": "CUST123",
        "account_number": "ACC456",
        "tools": {
            "validate_customer": validate_customer
        }
    }
)

# Step 3: Call Claude with orchestration

# Step 4: Print result
print("Validation Result:", validation)
```

- This is the **higher‑level orchestration API**.  
- `query()` wraps the raw `client.messages.create` call.  
- `ClaudeAgentOptions` manages tool permissions (`allowedTools`) and shared state (`context`).  
- You don’t manually handle `stop_reason` — the SDK abstracts that away.  
- This is easier to write, but less granular.

👉 This is the snippet with `from claude_agent_sdk import query, ClaudeAgentOptions`.

_Put your API key in the environment (export ANTHROPIC_API_KEY=...) before running your script. That’s how Claude knows how to connect to Anthropic’s API._

### Key Distinction
- **Raw agentic loop** → you write the execution loop, handle stop reasons, and tool calls yourself.  
- **SDK orchestration (`query`, `ClaudeAgentOptions`)** → you let the SDK manage the agent loop, context passing, and tool spawning for you.  

Both ultimately call Claude under the hood via `client.messages.create`. The difference is **how much control you want**:
- Raw loop = maximum control, more code.  
- SDK = convenience wrapper, less code.  


✅ So yes: the previous example (with `client.messages.create` and `stop_reason`) and the `from claude_agent_sdk import query, ClaudeAgentOptions` example are **different styles of agentic programming**. One is raw Anthropic SDK, the other is the higher‑level Claude Agent SDK wrapper.  


## Two Modes of `query()` in the Claude Agent SDK

- **Synchronous mode**  
  ```python
  result = query("Validate customer for KYC.", options)
  print(result)
  ```
  ➝ Here, `query()` runs once, waits for Claude to finish, and returns the final result.  
  ➝ This is blocking — you don’t see intermediate output.

- **Streaming (async) mode**  
  ```python
  async for message in query(
      prompt="Use the code-reviewer agent to review this codebase",
      options=ClaudeAgentOptions(...),
  ):
      print(message)
  ```
  ➝ Here, `query()` is an **async generator**.  
  ➝ You iterate over it with `async for`, and each `message` is yielded as Claude produces output.  
  ➝ This lets you process results in real time (like logs, partial completions, or multi‑agent coordination).


### So, Is `query` Synchronous or Streaming?

- **By default** → `query()` is synchronous: it returns the final result once Claude finishes.  
- **When used with `async for`** → `query()` acts as a streaming async generator: you get messages as they arrive.  

👉 That’s why in your earlier `validate_customer` example, you saw a simple synchronous call.  
👉 In the `code-reviewer` / `test-writer` example, you saw the streaming form — because multi‑agent orchestration often benefits from incremental output.


### 📘 Key Takeaway
- **Synchronous `query()`** → one final result, blocking.  
- **Streaming `query()`** → async generator, yields messages progressively.  


✅ So: `query` isn’t *always* synchronous — it can be used both ways. In your snippet with `async for`, it’s explicitly the **streaming async version**.

Here’s a **structured notes section** that clarifies the concepts of **context** vs **session** in agentic workflows:


# 📘 Context vs Session in Agentic Systems

### 🔹 **Context**
- **Definition** → Context is the *data payload* passed between agents or tools. It contains the information needed for reasoning.  
- **Scope** → Narrow and task‑specific. It can include:
  - Inputs (customer ID, account number, document text).  
  - Structured findings (claims + metadata).  
  - Shared state (tool mappings, variables).  
- **Best Practice** → Separate **content** (claims, outputs) from **metadata** (sources, timestamps, attribution).  
- **Lifecycle** → Context is ephemeral — it exists only for the duration of the task or workflow.  

👉 Example:  
```json
{
  "customer_id": "CUST789",
  "account_number": "ACC101",
  "findings": [
    {
      "claim": "Revenue increased 15% YoY",
      "evidence": "Q4 earnings report, page 3",
      "source_url": "https://example.com/earnings",
      "document_name": "Q4 2024 Earnings Report",
      "publication_date": "2025-01-15"
    }
  ]
}
```


### **Session**
- **Definition** → A session is the *execution environment* where agents operate. It defines the sandbox, tools, and agents available.  
- **Scope** → Broad and persistent across multiple queries.  
- **Best Practice** → Use `fork_session` to branch from a baseline session when exploring divergent workflows.  
- **Lifecycle** → Sessions can persist across multiple queries, but forked sessions are isolated from each other.  

👉 Example:  
```python
# Forked sessions from the same baseline
kyc_session = fork_session(options)
credit_session = fork_session(options)
```


### Key Differences

| Aspect | **Context** | **Session** |
|--------|-------------|-------------|
| **Definition** | Data payload passed between agents/tools | Execution environment for agents |
| **Scope** | Narrow, task‑specific | Broad, persistent |
| **Lifecycle** | Ephemeral, tied to a single workflow | Can persist, forked for divergence |
| **Purpose** | Provides inputs and structured findings | Provides sandbox, tools, and agent definitions |
| **Best Practice** | Separate content from metadata | Use forked sessions for parallel workflows |


### Banking Workflow Example
- **Context** → Customer ID + account number + structured findings (KYC status, fraud check result, credit score).  
- **Session** → Defines agents (`customer-validator`, `credit-scorer`) and tools (`call_kyc_service`, `Bash`, `call_credit_service`).  
- **Forked Sessions** → Run KYC validation and credit scoring in parallel, each with its own isolated execution environment.  
- **Merged Context** → Combine outputs into a structured JSON decision object for loan approval.


### Key Takeaway
- **Context = the data you pass.**  
- **Session = the environment you run in.**  
- Context is ephemeral and task‑specific, while sessions are persistent and can be forked for parallel or divergent workflows.  
- Keeping them distinct ensures clarity, auditability, and clean orchestration in multi‑agent systems.


✅ This distinction is crucial: **context is about *what* agents reason over, session is about *where* they reason.**  

## What `fork_session` Does
- **Baseline snapshot** → You start with a shared context (tools, agents, state).  
- **Fork** → You create a new session branch using `fork_session`.  
- **Independence** → Each branch can explore a different approach, run different agents, or call different tools.  
- **Isolation** → Results in one branch don’t leak into the other. They’re sandboxed.  


### Why It’s Useful
- **Exploring divergent strategies** → e.g., one branch runs a `customer-validator` agent, another runs a `credit-scorer`.  
- **Parallel experimentation** → test multiple hypotheses or workflows at once.  
- **Auditability** → you can attribute outputs to the correct branch without cross‑contamination.  


### Banking Scenario Example with `fork_session`

```python
from claude_agent_sdk import fork_session, query

credit_session = fork_session(options)

# Run KYC validation in one branch

    prompt="Use the customer-validator agent to validate customer CUST789 with account ACC101",
    options=kyc_session,

    print("[KYC Branch]", message)

    prompt="Use the credit-scorer agent to fetch credit score for customer CUST789",

```


### What Happens
- Both branches start from the same **baseline context** (tools, agents).  
- **KYC branch** runs the external API + Bash fraud script.  
- **Credit branch** runs the credit scoring API.  
- Each branch has its own message stream, with outputs attributed separately.  
- You can later **merge results manually** (e.g., combine KYC + credit score into a loan decision).  


### Key Takeaway
- `fork_session` = **branching analysis**.  
- Use it when you want to explore multiple workflows in parallel without them interfering.  
- In banking: one branch for **KYC**, one for **fraud detection**, one for **credit scoring** — all independent, but starting from the same baseline.  


✅ So: `fork_session` is your way to run **parallel, isolated agent sessions** from a shared starting point.

Here’s a **Claude Exam–compatible study note** for **Workflow Enforcement and Handoff (Section 1.4)**. I’ve structured it in exam‑style clarity, highlighting the critical distinctions and best practices:


## Workflow Enforcement and Handoff

### The Critical Distinction
This is one of the most heavily tested concepts:

| **Enforcement Type** | **When to Use** | **Guarantee Level** |
|-----------------------|-----------------|----------------------|
| **Programmatic** (hooks, prerequisites) | Financial or safety consequences | Deterministic — 100% enforced |
| **Prompt-based** (instructions) | Best‑effort acceptable | Probabilistic — non‑zero failure rate |


### Example: Financial Operations
**Scenario:** A customer support agent must verify identity before processing refunds.

- **Wrong approach (prompt‑based):**  
  `"Always verify the customer's identity before processing any refund."`  
  → Works most of the time, but has a non‑zero failure rate. For financial operations, “most of the time” is **not acceptable**.

- **Correct approach (programmatic):**  
  A **PreToolUse hook** on `process_refund` checks whether `get_customer` has been called and returned a verified customer ID.  
  → If not, the hook blocks the refund with **exit code 2**.  
  → Deterministic enforcement ensures **no refund without identity verification**.


#### Handoff to Humans
When an agent escalates to a human, the human typically does **not** have access to the full transcript.  
The handoff must include a **structured summary**:

```json
{
  "customer": "Jane Doe (#12345)",
  "issue": "Damaged product received",
  "order": "#67890, $149.99, placed 2024-01-15",
  "root_cause": "Shipping damage",
  "actions_taken": "Verified order, confirmed damage via photos",
  "recommended_action": "Full refund + replacement shipment",
  "refund_amount": "$149.99"
}
```

- **Content** → Customer, issue, order details, root cause.  
- **Metadata** → Actions taken, recommended resolution, refund amount.  
- **Best Practice** → Always pass structured context so the human can act without needing the full transcript.


## Key Takeaways for Exam
- **Programmatic enforcement** = deterministic, required for financial/safety workflows.  
- **Prompt‑based enforcement** = probabilistic, acceptable only when failure is tolerable.  
- **Human handoff** must include **structured summaries**, not raw transcripts.  
- **Exam tip:** Always choose programmatic enforcement for **refunds, payments, safety checks**.  


## Workflow Event Groups & Examples

### **Setup**
- **Events:** `Setup`  
- **Purpose:** Runs once per session to initialize environment.  
- **Example:** Load agent definitions, configure tools, set working directory.  
  ```text
  Setup → Initialize banking agents and load fraud detection scripts
  ```


### **Session & Turn**
- **Events:** `SessionStart ★`, `SessionEnd ★`, `UserPromptSubmit ★`, `UserPromptExpansion`, `Stop ★`, `StopFailure`  
- **Purpose:** Manage lifecycle of a session and individual turns.  
- **Examples:**  
  - `SessionStart` → New customer validation workflow begins.  
  - `UserPromptSubmit` → Customer asks for refund.  
  - `Stop` → Agent finishes execution successfully.  
  - `StopFailure` → Agent halts due to missing prerequisites.


### **Tool / Agentic Loop**
- **Events:** `PreToolUse ★`, `PostToolUse ★`, `PostToolUseFailure`, `PostToolBatch`, `PermissionRequest ★`, `PermissionDenied`  
- **Purpose:** Track tool usage and enforcement.  
- **Examples:**  
  - `PreToolUse` → Check if identity verified before refund tool runs.  
  - `PostToolUse` → Log refund processed successfully.  
  - `PermissionRequest` → Agent asks to run Bash command.  
  - `PermissionDenied` → Policy blocks unsafe command.


### **Agent & Task**
- **Events:** `SubagentStart`, `SubagentStop ★`, `TaskCreated`, `TaskCompleted`, `TeammateIdle`  
- **Purpose:** Manage subagents and task execution.  
- **Examples:**  
  - `SubagentStart` → Credit scorer agent begins.  
  - `TaskCreated` → Fraud check task initialized.  
  - `TaskCompleted` → Fraud check returns “clear.”  
  - `SubagentStop` → Credit scorer agent finishes.


### **File & Config**
- **Events:** `FileChanged`, `CwdChanged`, `ConfigChange`, `InstructionsLoaded`  
- **Purpose:** Track environment changes.  
- **Examples:**  
  - `FileChanged` → Customer data file updated.  
  - `CwdChanged` → Switch working directory to `/src/banking`.  
  - `ConfigChange` → Update fraud detection thresholds.  
  - `InstructionsLoaded` → Load new refund policy instructions.


### **Compaction**
- **Events:** `PreCompact ★`, `PostCompact`  
- **Purpose:** Manage memory compaction and transcript trimming.  
- **Examples:**  
  - `PreCompact` → Before transcript is shortened.  
  - `PostCompact` → After transcript trimmed, summary stored.


### **Context & Worktree**
- **Events:** `Notification`, `MessageDisplay`, `Elicitation`, `ElicitationResult`, `WorktreeCreate`, `WorktreeRemove`  
- **Purpose:** Handle context passing and worktree lifecycle.  
- **Examples:**  
  - `Notification` → Alert: “Refund requires manager approval.”  
  - `MessageDisplay` → Show structured handoff summary to human.  
  - `Elicitation` → Ask customer for missing account number.  
  - `ElicitationResult` → Customer provides account number.  
  - `WorktreeCreate` → New branch for credit scoring.  
  - `WorktreeRemove` → Delete fraud detection branch after completion.


### Key Takeaways
- **Groups** organize events by workflow stage (setup, session, tool use, agent tasks, file/config, compaction, context/worktree).  
- **Starred events (★)** are critical for exam questions — they represent deterministic checkpoints.  
- **Examples** help you remember how each event applies in real workflows (banking, refunds, fraud checks).

## Session Event Flow

```
SessionStart
  → UserPromptSubmit
    → [Agentic Loop]:
        PreToolUse
          → PermissionRequest  (may fire PermissionDenied)
            → PostToolUse  /  PostToolUseFailure
              → SubagentStart / SubagentStop
                → TaskCreated / TaskCompleted
    → Stop  /  StopFailure
  → PreCompact → PostCompact
→ SessionEnd
```


### **Step‑by‑Step Meaning**

- **SessionStart** → A new agent session begins. Environment initialized.  
- **UserPromptSubmit** → User provides input (e.g., “Process refund for Jane Doe”).  
- **Agentic Loop** → The agent decides which tools/agents to call.  
  - **PreToolUse** → Enforcement hook. Check prerequisites (e.g., identity verified).  
  - **PermissionRequest** → Agent asks to run a tool (like Bash).  
    - **PermissionDenied** → Policy blocks unsafe tool use.  
  - **PostToolUse** → Tool succeeded.  
  - **PostToolUseFailure** → Tool failed.  
  - **SubagentStart** / **SubagentStop** → Track subagent lifecycle.  
  - **TaskCreated** / **TaskCompleted** → Track task lifecycle.  
- **Stop** → Agent finishes successfully.  
- **StopFailure** → Agent halts due to error.  
- **PreCompact** → Transcript about to be trimmed.  
- **PostCompact** → Transcript trimmed, summary stored.  
- **SessionEnd** → Session closes.


### **How to Use This Flow**

- **Exam context:** You’ll often be asked *which enforcement type applies at which event*.  
  - **Programmatic enforcement** → `PreToolUse` (deterministic).  
  - **Prompt‑based enforcement** → instructions inside `UserPromptSubmit` (probabilistic).  
- **Logging & auditing:** Attach handlers to `SessionStart`, `Stop`, `SessionEnd` for compliance.  
- **Human handoff:** Trigger at `MessageDisplay` or after `StopFailure`, passing a structured summary.  
- **Parallel workflows:** Use `SubagentStart`/`TaskCreated` to track forked sessions.  
- **Transcript management:** Use `PreCompact`/`PostCompact` to summarize before trimming.


### Key Takeaways
- This flow is the **backbone of agent lifecycle**.  
- **Starred events (★)** are exam‑critical checkpoints.  
- **PreToolUse** is where deterministic enforcement happens.  
- **SessionEnd** always closes the loop, regardless of success or failure.
