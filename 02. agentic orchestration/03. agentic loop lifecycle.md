# 02. The Agentic Loop Lifecycle

## 01. API Request Structure

The Claude API follows a **request–response model**, meaning every request must include **structured fields** that define how the model behaves, what context it sees, and which tools it can use.  

### Why This Matters
- **Model** → Selects the Claude variant; exam trap: unsupported names cause request failure.  
- **Max Tokens** → Hard Caps single response length; exceeding triggers, truncated output, stop_reason `"max_tokens"`.  
- **System Prompt** → Defines assistant persona; exam trap: confusing with assistant role.  
- **Messages** → Ordered conversation history; must be sequential and role‑tagged.  
- **Tools** → Declares available external functions; schema must match.  
- **Tool Choice** → Controls auto/manual tool invocation; exam trap: assuming auto is default.  

```json
{
  "model": "claude-sonnet-4-6",        // Model version
                                       // Key Concept: must be valid + supported
                                       // Exam Trap: using unsupported model name → request fails

  "max_tokens": 1024,                  // Token budget for response
                                       // Key Concept: caps output length
                                       // Exam Trap: exceeding → stop_reason = "max_tokens"

  "system": "You are a helpful assistant.", 
                                       // System prompt
                                       // Key Concept: sets assistant persona/role
                                       // Exam Trap: confusing system vs assistant role

  "messages": [                        // Conversation history
                                       // Key Concept: sequential, role-tagged
                                       // Exam Trap: missing role tags → invalid request
    {"role": "user", "content": "Hi!"},
    {"role": "assistant", "content": "Hello!"},
    {"role": "user", "content": "How are you?"}
  ],

  "tools": [...],                      // Tool definitions
                                       // Key Concept: declares available external functions
                                       // Exam Trap: forgetting to inject tool_result after execution

  "tool_choice": {"type": "auto"}      // Tool selection strategy
                                       // Key Concept: auto = model decides tool use
                                       // Exam Trap: assuming auto is default → must be explicit
}
```

### Max Tokens Exceeded

#### What It Means
- **Max Tokens** is the **hard cap** on how many tokens Claude can generate in a single response.  
- When the model hits this ceiling, the output is **truncated** and the API returns `stop_reason = "max_tokens"`.  
- Forgetting that max_tokens only affects output length, not the total context window.
- Asking for “everything at once” → guaranteed truncation.
- Architect resends the request with prior messages and instructs Claude to “continue from where you left off.”
- Forgetting to summarize → context window overflow or repeated truncation.

#### Impact
- **Truncated Output** → Response may cut off mid‑sentence or mid‑workflow.  
- **Incomplete Tasks** → Reports, code, or multi‑step reasoning may stop halfway.  
- **Loop Control** → Architect must decide whether to continue, summarize, or chunk.  


#### ⚠️ Common Exam Traps
- **Confusing `max_tokens` with context window** →  
  - `max_tokens` = output length limit.  
  - Context window = total input + output capacity.  
- **Assuming model “refused”** → It didn’t refuse, it just hit the cap.  
- **Not handling continuation** → Forgetting to resend with higher limit or chunking.  


#### Recovery Strategies
- **Increase Limit** → Raise `max_tokens` if longer output is acceptable.  
- **Chunk Task** → Break request into smaller parts (e.g., sections of a report).  
- **Continuation Loop** → Ask Claude to continue from where it left off.  
- **Summarization** → Compress prior content before retrying.  


#### Possible Exam Questions

- **Stop Reason Identification**  
  *Question:* “Which stop_reason indicates Claude’s output was truncated due to hitting the configured token ceiling?”  
  *Answer:* `max_tokens`.

- **Architect Response**  
  *Question:* “When Claude stops with `stop_reason = max_tokens`, what strategies can an architect apply to continue the workflow?”  
  *Answer:* Increase `max_tokens`, chunk the task, use continuation loops, or summarize prior content.

- **Difference vs Context Window**  
  *Question:* “How does `max_tokens` differ from `model_context_window_exceeded`?”  
  *Answer:* `max_tokens` = output length cap; `model_context_window_exceeded` = total input + output exceeds model’s context window.

- **Exam Trap Scenario**  
  *Question:* “A developer sees truncated output and assumes Claude refused the request. What is the correct interpretation?”  
  *Answer:* It hit `max_tokens`, not a refusal — the architect must handle continuation.

- **Workflow Continuation**  
  *Question:* “In a compliance report generation task, Claude stops at section 40 with `max_tokens`. What should the architect do?”  
  *Answer:* Summarize sections 1–40, then continue with sections 41–100.

- **Cost vs Completeness**  
  *Question:* “What trade‑off does an architect face when raising `max_tokens`?”  
  *Answer:* Higher cost vs. more complete output.


### Missing `system` Field

#### What Happens
- **Default Persona** → Claude defaults to a generic “helpful assistant” role.  
- **Loss of Control** → You lose the ability to enforce tone, style, or constraints globally.  
- **Exam Trap** → Students often assume `system` is optional. In practice, omitting it means you cannot guarantee consistent persona or policy adherence.


#### 🔹 Why `system` Matters
- **Persona Control** → Defines assistant’s role (e.g., teacher, financial advisor, legal analyst).  
- **Policy Enforcement** → Ensures refusals, safety rules, or compliance constraints are applied consistently.  
- **Consistency Across Turns** → Without `system`, the assistant may drift in style or behavior.  


#### Exam Perspective
  - *Question:* “What is the impact of omitting the `system` field in a Claude API request?”*  
    **Answer:** Claude defaults to a generic persona; architect loses control over tone, style, and policy enforcement.  


#### ⚠️ Common Exam Traps
- Writing persona instructions inside `messages` instead of `system`.  
- Assuming `system` is optional in exam scenarios — it’s often required to demonstrate control.  
- Forgetting that `system` applies globally, not just to one turn.  


### Missing `messages` Field

#### What Happens
- **No Conversation Context** → Claude has no dialogue history to reference.
- **Cold Start** → The model treats the request as if it’s the very first turn, ignoring prior exchanges.
- **Exam Trap** → Students often assume `system` alone is enough. In reality, `messages` is mandatory for conversation continuity.


### Why `messages` Matters
- **Sequential History** → Ensures Claude sees the full back‑and‑forth (user + assistant).
- **Role Tags** → Each entry must be tagged (`user`, `assistant`, `system`). Missing tags = invalid request.
- **State Management** → Without `messages`, the agentic loop cannot evolve — tool results, stop reasons, and prior context vanish.



#### Exam Perspective
  *Question:*“What is the impact of omitting the `messages` field in a Claude API request?”*
  - **Answer:** Claude loses conversation history, defaults to cold start, and cannot maintain state continuity.

- **Question Example:**  
  *“Which field defines the conversation history, and what happens if it’s missing?”*  
  - **Answer:** `messages` defines history; if missing, Claude ignores prior turns and starts fresh.  



#### ⚠️ Common Exam Traps
- Forgetting **role tags** → invalid JSON.  
- Assuming `system` replaces `messages`.  
- Not appending **tool_result** into `messages` → breaks loop continuity.  
- Treating `messages` as optional — it’s required for multi‑turn workflows.  



###  Missing `tool_result` Injection

- **Breaks Loop Continuity**
  Without `tool_result`, the model has no structured feedback from the tool. It cannot reason about the outcome, leading to hallucinations or repeated tool calls.

- **Runaway Loops**
  The model may keep re‑issuing the same `tool_use` request because it never sees the result injected back. This is a classic **exam trap**: infinite tool calls due to missing result injection.

- **Loss of State**
  The conversation state becomes inconsistent. The assistant “thinks” the tool was never executed, so reasoning diverges from reality.

- **Stop Reason Misinterpretation**
  If results aren’t injected, the model may misinterpret `stop_reason` (e.g., treating `tool_use` as unresolved instead of completed).  

- **Exam Trap Example**
  *Scenario:* A workflow validates a customer account. The tool executes correctly, but the developer forgets to inject `tool_result`.  
  - **Expected:** Model consumes result → “Customer valid.”  
  - **Actual:** Model retries tool endlessly → runaway loop.  
  - **Exam Answer:** Always inject `tool_result` to prevent infinite retries.  

#### ⚠️ Common Exam Traps
- Forgetting **role tags** in `messages`.
- Misusing `system` vs `assistant`.
- Exceeding `max_tokens` → truncated output.
- Omitting `tool_result` injection after tool execution.
- Assuming `tool_choice` defaults to auto.
- Forgetting `tool_result` → infinite loop.
- Injecting result as plain text instead of structured `tool_result`.
- Misplacing role (`assistant` vs `user`) when appending tool results.
- Assuming tool execution alone is enough — **injection is mandatory**.


### Missing `tools` Field

#### What Happens
- **No External Capabilities** → Claude can only generate text; it cannot call APIs, run code, or interact with external systems.  
- **Pure Text Mode** → The agentic loop is reduced to reasoning + text output only.  
- **Exam Trap** → Students assume Claude can “just use tools” by default. In reality, tools must be explicitly declared in the request.



#### Why `tools` Matters
- **Extends Functionality** → Enables Claude to perform actions (search, memory, email, healthcare, etc.).  
- **Schema Binding** → Each tool must have a schema so Claude knows how to call it.  
- **Agentic Loop Continuity** → Without tools, stop reasons like `tool_use` never occur — the loop is limited to text.  



#### Exam Perspective
- **Question:** *“What is the impact of omitting the `tools` field in a Claude API request?”*  
  **Answer:** Claude cannot call external functions; it operates in pure text mode only.  

- **Question:** *“Which field declares external functions, and what happens if it’s missing?”*  
  **Answer:** `tools` declares functions; if missing, Claude cannot execute tool calls and will only generate text.  



#### ⚠️ Common Exam Traps
- Assuming tools are “built‑in” — they must be declared.  
- Forgetting to provide **input schema** → Claude cannot reason about tool parameters.  
- Confusing `tool_choice` with `tools` — `tool_choice` only controls selection, but tools must exist first.  
- Expecting `tool_use` stop_reason without tools defined — impossible.  



## 1.2 Message Roles

The `messages` array uses two conversational roles, while system instructions are provided separately through the `system` parameter:

* `user` — user messages, including **tool results**. Tool results are sent as a `tool_result` content block inside a `user`-role message, **not** as a separate `tool` role.
* `assistant` — Claude's responses, including tool-use requests represented by `tool_use` content blocks.
* `system` — system-level instructions provided through the top-level `system` parameter.

The tool request from Claude is represented as a `tool_use` content block in an `assistant` message:

```json
{
  "role": "assistant",
  "content": [
    {
      "type": "tool_use",
      "id": "toolu_01...",
      "name": "get_weather",
      "input": {
        "city": "Mumbai"
      }
    }
  ]
}
```

And the corresponding Tool results are **not** sent using a separate `"tool"` message role. Instead, they are returned in a `user`-role message containing a `tool_result` content block:

```json
{
  "role": "user",
  "content": [
    {
      "type": "tool_result",
      "tool_use_id": "toolu_01...",
      "content": "..."
    }
  ]
}
```

### System Instructions

System instructions are provided through the top-level `system` field and apply from the beginning of the request:

```json
{
  "system": "You are a helpful assistant.",
  "messages": [
    {
      "role": "user",
      "content": "Hello"
    }
  ]
}
```

**Key distinction:**

```text
system     → Instructions / behavior
user       → User input + tool results
assistant  → Claude responses + tool-use requests
```

### Critically Important: Stateless API

The Messages API is **stateless**. Claude does not automatically persist conversation state between API requests.

Therefore, the application is responsible for maintaining the conversation history and sending the required history with subsequent requests.

**Exam/Interview takeaway:**

> **Claude does not automatically remember previous API requests. The application must maintain and provide the relevant conversation history on subsequent requests.**


## 02. Lifecycle Phases
1. **Request**
   - User provides input or task specification.
   - Starting point of the loop.

2. **Model Reasoning**
   - Model interprets intent and plans next step.
   - Decides whether knowledge suffices or a tool is needed.

3. **Tool Selection**
   - Chooses the most appropriate tool(s) based on schema and availability.
   - Critical exam point: selection must match task type (e.g., search vs. calculator).

4. **Tool Execution**
   - External system runs with given parameters.
   - Produces authoritative results.

5. **Tool Result**
   - Output injected back into conversation state as `tool_result`.
   - Ensures continuity and prevents hallucination.

6. **Next Model Turn**
   - Model consumes tool results.
   - Decides continuation (loop again) or termination.

```
import anthropic

client = anthropic.Anthropic()

# -------------------------------
# Define banking tool
# -------------------------------
tools = [
    {
        "name": "validate_customer",   # Tool name
        "description": "Validate customer account and KYC status",  # Purpose
        "input_schema": {              # Schema defines required inputs
            "type": "object",
            "properties": {
                "customer_id": {"type": "string"},
                "account_number": {"type": "string"}
            },
            "required": ["customer_id", "account_number"],  # Both must be provided
        },
    }
]

# -------------------------------
# Tool execution logic
# -------------------------------
def execute_tool(name, tool_input):
    if name == "validate_customer":
        # Simulated validation logic
        if tool_input["customer_id"] == "CUST123" and tool_input["account_number"] == "ACC456":
            return "Customer is valid: KYC complete, account active, no fraud flags."
        else:
            return "Customer validation failed: account inactive or KYC pending."
    return "unknown tool"  # Fallback if tool name not recognized

# -------------------------------
# Initial user request
# -------------------------------
messages = [{"role": "user", "content": "Validate customer CUST123 with account ACC456"}]

# -------------------------------
# Agentic execution loop
# -------------------------------
while True:
    response = client.messages.create(
        model="claude-sonnet-5",   # Model used for reasoning
        max_tokens=1024,           # Token budget
        tools=tools,               # Available tools
        messages=messages,         # Conversation history
    )

    # Append model response to conversation
    messages.append({"role": "assistant", "content": response.content})

    # -------------------------------
    # Interpret stop_reason
    # -------------------------------
    match response.stop_reason:

        case "tool_use":
            # Model requested tool execution → continue loop
            tool_results = []
            for block in response.content:
                if block.type == "tool_use":
                    # Execute tool with given input
                    result = execute_tool(block.name, block.input)
                    # Return tool result back into conversation
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": result,
                    })
            # Inject tool results for next model turn
            messages.append({"role": "user", "content": tool_results})
            continue  # Loop continues

        case "pause_turn":
            # Model paused → wait for next iteration
            continue

        case "end_turn" | "stop_sequence":
            # Model considers task complete → terminate loop
            final_text = "".join(b.text for b in response.content if b.type == "text")
            print(final_text)
            break

        case "max_tokens":
            # Token budget exceeded → truncate or retry
            print("Truncated — consider raising max_tokens or summarizing history.")
            break

        case "refusal":
            # Model refused task → reset or exit
            print("Refused:", response.stop_reason, getattr(response, "stop_details", None))
            messages = messages[:1]  # Reset to initial request
            break

        case "model_context_window_exceeded":
            # Context too large → trim history and retry
            print("Hit context window — trim or summarize `messages` and retry.")
            break
```

##### Tool vs Knowledge in Agentic AI

- **LLM knowledge** → Claude can directly answer general questions (e.g., “KYC = Know Your Customer, a regulatory identity verification process”).  
- **Tool invocation** → If a tool is defined (`whatIsKYC`), Claude may prefer calling it for **authoritative, structured, or policy-grounded answers**.  
- **Decision logic** →  
  - If the query is **generic** → respond directly with text.  
  - If the query matches a **tool schema** → emit `tool_use`.  
  - If both apply → Claude often **calls the tool first**, then enriches with its own knowledge.  
- **stop_reason** →  
  - `"end_turn"` → answered directly from knowledge.  
  - `"tool_use"` → invoked the tool.  
  - Hybrid → `"tool_use"` followed by `"end_turn"` after tool_result.  
- **Best practice** → Use tools for **specific, dynamic, or compliance-critical tasks**, and let LLM knowledge provide **contextual explanation**.

### Key Takeaways

- **Sequential Lifecycle**  
  Request → Reasoning → Selection → Execution → Result → Next Turn.  
  **Key Concept:** Always linear, no skipping phases.  
  **Exam Trap:** Writing “execution before reasoning” or omitting *tool result injection*.  

- **Stop Reasons** control loop flow:  
  - `tool_use` → Continue loop with tool execution.  
  - `end_turn` → Task complete, terminate safely.  
  - `pause_turn`, `refusal`, `max_tokens` → Special handling.  
  **Key Concept:** Stop reasons are **signals**, not errors.  
  **Exam Trap:** Confusing `tool_use` with “loop termination.”  

- **Tool Results Injection**  
  Must be returned into conversation as `tool_result`.  
  **Key Concept:** Ensures continuity of reasoning.  
  **Exam Trap:** Forgetting to inject results → model hallucinates state.  

- **Loop Control Mechanisms**  
  - Timeouts → Prevent resource drain.  
  - Iteration budgets → Cap maximum turns.  
  - Error thresholds → Abort after repeated failures.  
  **Key Concept:** Safety nets against runaway loops.  
  **Exam Trap:** Assuming “infinite retries” are allowed — they are not.  

- **Termination Criteria**  
  Explicit exit conditions:  
  - Task complete (natural end).  
  - Stop signal (user/system directive).  
  - Escalation (handoff to agent/human).  
  **Key Concept:** Every workflow must define an exit.  
  **Exam Trap:** Leaving termination implicit → risk of infinite loop.  


## ⚠️ Common Exam Traps
- Mixing up **reasoning vs. execution** order.  
- Forgetting **tool_result injection** step.  
- Treating `tool_use` as termination instead of continuation.  
- Assuming loops run indefinitely without **budgets/timeouts**.  
- Not stating **explicit termination criteria** in workflow design.  



## Interpreting `stop_reason`
- **tool_use** → Execute requested tool, continue loop.  
- **end_turn** → Model considers task complete, loop terminates.  
- **pause_turn** → Loop cap reached, architect must resend without new input.



## Returning Tool Results
- Results must be **injected** back into the conversation as `tool_result`.  
- Ensures continuity of reasoning and avoids hallucinated state.  
- Each result is treated as authoritative input for the next model turn.



## Loop-Control Mechanisms
- **Task-complete termination** → Natural end when output satisfies request.  
- **Explicit stop signals** → User or system directive halts loop.  
- **Error/failure thresholds** → Abort after repeated tool errors.  
- **Maximum turns / iteration budgets** → Safety cap on loop length.  
- **Timeout/resource limits** → Prevents runaway resource consumption.  
- **Escalation** → Hand off to another agent or human if unresolved.



## Runaway-Loop Prevention
- **Avoid infinite tool calls** → Detect repeated identical calls.  
- **Limit retries** → Cap on failed attempts.  
- **Define clear termination criteria** → Ensure every workflow has an exit condition.
