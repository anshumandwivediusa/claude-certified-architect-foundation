# 02. Foundational Agent Concepts

**Agentic architecture** is the foundational design pattern behind modern AI systems that can work **autonomously (no human or logic dependent) toward a goal**. Instead of simply answering questions, these systems can **goal**, **plan**, **reason**, **take actions**, **evaluate outcomes**, and **adapt their approach** until the task is successfully completed.

Traditional chatbots follow a simple request-response model: the user asks a question, the model generates a single answer, and the interaction ends. Agentic systems, however, are designed for **goal-oriented execution** rather than **one-time response generation**. They continuously analyze the current state of a task, decide what to do next, use available tools when necessary, assess the results of those actions, and repeat the process until the objective is achieved or human intervention is required.

In other words, a traditional chatbot focuses on **"What should I answer?"**, whereas an agentic system focuses on **"What should I do next to accomplish the goal?"** This shift from generating responses to executing tasks is what distinguishes agentic architecture from conventional conversational AI.

For example:

* **Traditional Chatbot:**
  *User:* "Write a Python function to reverse a string."
  *Behavior:* Generates the function and stops.

* **Agentic System (Claude Code):**
  *User:* "Upgrade my Python project to Python 3.13, fix any compatibility issues, run the tests, and update the documentation."
  *Behavior:* Reads the project, creates a plan, modifies multiple files, runs tests, analyzes failures, applies fixes, updates documentation, and finally presents a summary of the completed work.

This ability to **Goal → Plan → Reason → Act → Evaluate → Adapt → Repeat → Complete** is the defining characteristic of an agentic architecture and forms the foundation of autonomous AI systems such as Claude Code.

For the Claude Code Architect Foundation exam, candidates should understand:

* The characteristics of an AI agent and how it differs from a traditional chatbot or workflow.
* The architecture of iterative reasoning and execution loops.
* The role of planning, observation, action, and evaluation during task execution.
* How execution models determine task decomposition, orchestration, and completion.
* The relationship between the agent, tools, memory, permissions, and human oversight.
* When autonomous execution is appropriate versus when human approval or intervention is required.

A solid understanding of agentic architecture and execution models provides the conceptual foundation for every other topic in the certification, including multi-agent systems, tool orchestration, context management, reliability, and governance.


## 01. Distinguishing agents from workflows and conversational systems

- **Conversational systems**: single-turn or multi-turn text exchange, no autonomous action, no tool-driven state change — the model reasons *about* the world but doesn't act *in* it
- **Workflows**: pre-defined, deterministic sequences of steps (often LLM-augmented at individual steps) where the *path* is fixed in advance by the developer, even if individual outputs vary
- **Agents**: the model itself decides the path — which tools to call, in what order, whether to continue or stop — based on intermediate results, not a pre-scripted sequence
- The core distinguishing question: **"Who decides the next step — the developer at design time, or the model at run time?"**
- Recognizing hybrid systems: many production systems are workflows with an agentic sub-step (or vice versa), and part of the architectural skill is identifying which parts of a system need agentic flexibility and which don't

## 02. The four pillars of agentic behavior

- **Perception** — how the agent takes in the current state: user input, tool results, environment feedback, prior context
- **Cognition/(Selection or Reasoning)** — the decision-making step where the model interprets perceived state against its goal and chooses an action (which tool, which argument values, or whether to respond directly)
- **Action/Execution** — actually carrying out the chosen action (calling a tool, running code, hitting an API)
- **Iteration** — feeding the result of execution back into perception, closing the loop, and deciding whether the goal is met or another cycle is needed
- Architecturally, each pillar is a place where failure can be introduced — e.g., bad perception (stale or incomplete context), flawed selection (poor reasoning due to ambiguous tool descriptions), broken execution (tool errors not surfaced properly), or runaway iteration (no clear stopping condition)

## 03. How tool use closes the gap between an LLM and the "action environment"

- Without tools, an LLM only produces text — it can *describe* an action but not *perform* one.
- By default, Claude is a large language model (LLM). In this mode, it can only generate text outputs. That means it can describe an action — for example, “to calculate 42 × 17, multiply the two numbers” — but it cannot actually perform the calculation or fetch live data. Its knowledge is limited to what’s encoded in its parameters and what fits inside the context window. When Claude is connected to tools (like APIs, databases, or calculators), its role changes. Instead of just describing an action, Claude can decide when a tool is needed, format a request in the right schema, and send it out. The tool executes the action, and Claude then interprets the result back into natural language.
For example:
  - Without tools → “Tesla’s stock price can be checked on a finance website.”
  - With tools → Claude calls a stock API, retrieves the actual price, and presents it directly.
- Tool use gives the model a structured way to request a real-world side effect (an API call, a file write, a database query) and receive a real-world result back
- This is the mechanism that turns a "text generator" into something that can genuinely operate on external systems — the model's output becomes an *intent to act*, which the surrounding system executes and reports back on
- Key related concepts:
  - The tool call/observation cycle — request → execution → observation → next reasoning step
  - Why tool *description quality* matters here: the model can only act as well as it can understand what a tool does and when to use it (this connects directly into Domain 2, Tool Design & MCP)
  - The difference between the model *proposing* an action (via a tool_use block) and the *system* actually executing it — the model itself never directly touches the environment; execution is always mediated

## 04. Claude API, Claude Code, and Claude Agentic API

These terms are related but not interchangeable, and understanding the distinction is important for exam-level architectural thinking.

- **Claude API**: the model access layer. This is the interface for sending prompts, tool definitions, and context to Anthropic’s models. The API provides the reasoning engine, but by itself it does not automatically plan, execute, or manage long-running tasks.
- **Claude Code**: a product-level coding agent built for software work. It operates in a developer environment, can read and edit files, run terminal commands, inspect project state, iterate on failures, and summarize work. It is a concrete example of an agent acting in a real execution environment.
- **Claude Agentic API**: the orchestration layer for building agentic applications. It focuses on runtime behavior such as multi-step task execution, tool invocation, state tracking, memory, delegation, and human approval boundaries. In other words, it is the infrastructure for composing agent behavior into an application rather than a single standalone chatbot experience.

### Key distinction

- The **API** provides the model capability.
- **Claude Code** is a specific agent experience built on top of that capability.
- The **Agentic API** is the architecture pattern and runtime platform for designing and operating autonomous workflows around the model.

A useful mental model is:

- **Chatbot** = ask and answer
- **Claude API** = access to the model
- **Claude Code** = an agent that acts in a coding environment
- **Agentic API** = framework for orchestrating autonomous, tool-driven behavior

This distinction matters because many systems look similar from the outside but differ in who decides the next action: the developer at design time, or the model at runtime.


## Example

```python
import anthropic
import concurrent.futures

client = anthropic.Anthropic()

# Define available tools (the agent can choose among these)
tools = [
    {
        "name": "validate_customer",
        "description": "Validate customer account and KYC status",
        "input_schema": {
            "type": "object",
            "properties": {
                "customer_id": {"type": "string"},
                "account_number": {"type": "string"}
            },
            "required": ["customer_id", "account_number"],
        },
    },
    {
        "name": "get_weather",
        "description": "Fetch current weather for a city",
        "input_schema": {
            "type": "object",
            "properties": {
                "city": {"type": "string"}
            },
            "required": ["city"],
        },
    }
]

# Tool execution logic: this is the "action environment"
def execute_tool(name, tool_input):
    if name == "validate_customer":
        if tool_input["customer_id"] == "CUST123" and tool_input["account_number"] == "ACC456":
            return "Customer valid: KYC complete, account active."
        return "Customer validation failed."

    elif name == "get_weather":
        if tool_input["city"].lower() == "austin":
            return "Austin weather: 32°C, sunny."
        return f"Weather data not available for {tool_input['city']}."

    return "Unknown tool"

# Initial user request
messages = [
    {
        "role": "user",
        "content": "Validate customer CUST123 with ACC456 and check weather in Austin"
    }
]

# Agentic execution loop
while True:
    # 1. PERCEPTION
    # The model sees the current state: user request + prior conversation/tool outputs
    response = client.messages.create(
        model="claude-sonnet-5",
        max_tokens=1024,
        tools=tools,
        messages=messages,
    )

    # Add assistant response to message history
    messages.append({"role": "assistant", "content": response.content})

    # 2. COGNITION / SELECTION
    # The model decides whether to call tools or produce final output
    if response.stop_reason == "tool_use":
        tool_calls = [block for block in response.content if block.type == "tool_use"]

        tool_results = []

        # 3. ACTION
        # Execute tool calls in parallel to simulate real-world side effects
        with concurrent.futures.ThreadPoolExecutor() as executor:
            futures = []
            for block in tool_calls:
                futures.append(
                    executor.submit(execute_tool, block.name, block.input)
                )

            for block, future in zip(tool_calls, futures):
                result = future.result()
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": result,
                })

        # 4. ITERATION
        # Feed tool outputs back into the model so it can reason again
        messages.append({"role": "user", "content": tool_results})
        continue

    elif response.stop_reason == "end_turn":
        final_text = "".join(
            block.text for block in response.content if getattr(block, "type", None) == "text"
        )
        print("Final Output:", final_text)
        break

    else:
        print("Unexpected stop reason:", response.stop_reason)
        break
```

What this example is doing:
- The user gives a goal: “Validate customer CUST123 with ACC456 and check weather in Austin.”
- The model does not just answer directly.
- Instead, it decides whether it needs to use tools.
- It calls real tools, observes the results, and then continues reasoning until it can produce a final answer.

This matches the AI agent concept perfectly.

How it maps to agentic behavior:

- Perception
  - The model sees the current user request and prior messages.
  - It also knows what tools are available.

- Cognition / Reasoning
  - It decides:
    - “I need to validate the customer”
    - “I also need to get the weather”
  - This is not a fixed script; the model chooses actions dynamically.

- Action / Execution
  - The code executes `validate_customer` and `get_weather`.
  - These are external actions against a system or API-like environment.

- Observation
  - Tool outputs are returned:
    - Customer valid: KYC complete, account active.
    - Austin weather: 32°C, sunny.

- Iteration
  - The tool results are fed back into the conversation history.
  - The model reasons again and produces the final response.

Why this is an AI agent and not just a chatbot:
- A chatbot usually does: input → generate answer
- An agent does: input → reason → choose tools → act → observe → adapt → continue until goal is achieved

This example is agentic because:
- It has a goal
- It uses tools
- It acts on the environment
- It observes results
- It loops until completion

Not a workflow:
- A workflow is usually a fixed sequence of steps.
- Here, the model chooses what to do next at runtime.
- The developer did not hardcode:
  - “first validate customer”
  - “then get weather”
- The model decides that based on the goal and available tools.

This is a classic agentic loop:
- Goal
- Perceive
- Reason
- Act
- Observe
- Evaluate
- Repeat
- Complete

Example of the loop in plain English:
- User asks to validate a customer and check weather.
- Agent sees this goal.
- It calls `validate_customer` and `get_weather`.
- It receives results.
- It combines them into a final answer:
  - “The customer is valid and the weather in Austin is 32°C, sunny.”

Conceptually, this is the heart of an AI agent:
- It is not just producing text.
- It is making decisions and taking actions in an external environment.

So in one sentence:
- This code demonstrates an AI agent as a goal-driven system that uses tools, takes actions, evaluates results, and iterates until it completes the task.


### Q: Where is the planner in this implementation?

Answer: There is no dedicated planner component. The client.messages.create() call acts as an implicit planner. Claude analyzes the user request, determines which tools are needed, generates tool invocations, and replans after receiving tool results. The Python while loop serves as the orchestrator, while execute_tool() serves as the executor. This architecture follows a ReAct-style agent pattern where planning and reasoning are embedded within the model rather than implemented as a separate planner service.

### Mapping Agent Architecture

## 1. Agent Architecture Mapping

| Agent Layer                      | Code Location                                                                           | Responsibilities                                                                                                                                                                                                     |
| -------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Planner / Reasoning**          | `client.messages.create(...)`                                                           | Understands user intent, decomposes goals into tasks, develops an execution plan, identifies dependencies, decides when tools are needed, evaluates results, replans when necessary, and generates the final answer. |
| **Tool Selection**               | `response.stop_reason == "tool_use"` and `tool_use` blocks                              | Selects appropriate tools, maps requests to tool capabilities, generates tool parameters, determines execution order, identifies parallelizable tasks, and avoids unnecessary tool calls.                            |
| **Executor**                     | `execute_tool()`                                                                        | Executes business logic, invokes APIs and external systems, validates inputs, retrieves or updates data, handles operational errors, and returns execution results.                                                  |
| **Orchestrator**                 | `while True:`                                                                           | Controls the agent lifecycle, manages the ReAct loop, routes tool requests, coordinates execution, feeds observations back to the model, and determines when processing is complete.                                 |
| **Memory / Context**             | `messages`                                                                              | Maintains conversation history, user requests, assistant responses, tool calls, tool outputs, and the context needed for subsequent reasoning steps.                                                                 |
| **Environment**                  | `tools` and external systems                                                            | Defines available capabilities through tool schemas and provides access to APIs, databases, enterprise systems, and other external resources.                                                                        |
| **Observation Layer (Implicit)** | `tool_results`                                                                          | Captures tool outputs and execution outcomes, provides feedback to the planner, supports action validation, and supplies information for subsequent reasoning.                                                       |
| **Action Layer (Implicit)**      | `tool_use` content blocks                                                               | Represents the model's requested actions, bridges reasoning and execution, and initiates interactions with external systems through the executor.                                                                    |
| **Communication Layer**          | Final assistant response; commonly associated with `response.stop_reason == "end_turn"` | Presents the final answer, summarizes findings, combines relevant tool outputs, formats information, and communicates results to the user.                                                                           |

> **Note:** These mappings describe logical responsibilities, not necessarily separate classes or modules. In the Anthropic Messages API, `stop_reason` indicates why a response stopped. A `tool_use` stop reason means the model is requesting tool execution; `end_turn` indicates that the assistant turn is complete. Neither stop reason alone implements the corresponding architectural layer.

## 2. ReAct Mapping

ReAct stands for **Reason + Act**. It combines reasoning, action, and observation in an iterative loop.

| ReAct Step  | Code Component                                                       | Responsibility                                                                             |
| ----------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **Think**   | `client.messages.create(...)`                                        | Reasons about the current context, plans the next step, and decides whether to use a tool. |
| **Act**     | `execute_tool()`                                                     | Executes the requested tool operation.                                                     |
| **Observe** | `tool_results`                                                       | Collects execution results and feeds them back into the conversation.                      |
| **Repeat**  | `while True:`                                                        | Continues the reasoning-action-observation cycle until a stopping condition is reached.    |
| **Answer**  | Final assistant response, typically with `stop_reason == "end_turn"` | Returns the final response to the user.                                                    |

```
        User Request

      +--------------+
      | Think / Plan |
      |   LLM Call   |
      +--------------+
             |

      +--------------+
      | Tool Needed? |

        |          |

  +-----------+  +-------------+

```

## 4. Key Takeaway

An agent combines **reasoning, tool selection, execution, observation, memory, and orchestration** to accomplish a goal.

- **Reasoning** determines the next step.
- **Tool selection** identifies the required capability.
- **Execution** performs the requested operation.
- **Observation** returns the result.
- **Memory** preserves relevant context.
- **Orchestration** coordinates the overall loop.
- **Communication** delivers the final answer.
- **Environment** provides access to external capabilities.

Together, these components implement an agentic workflow that can iteratively act, evaluate results, and adapt until the goal is achieved or a stopping condition is reached.

Important interview point: `response.stop_reason == "tool_use"` is a signal to the application that the model has requested a tool, not the tool selector itself. Similarly, `while True:` implements a loop, but the orchestration logic inside that loop determines how the agent operates.
