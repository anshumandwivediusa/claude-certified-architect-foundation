# Claude Agentic SDK Cheat Sheet

## Overview

The Claude Agentic SDK is the higher-level orchestration layer built on top of the Messages API. It gives the architect:

- persistent agent objects
- environments for execution
- sessions for long-lived workflows
- event streaming
- native handling of tool execution
- structured stop reasons such as `requires_action` and `pause_turn`

The central idea is:

- The SDK manages the session lifecycle for you.
- Claude emits events while reasoning.
- Your application responds when Claude requests a tool or pauses.
- The loop continues until a terminal stop reason is reached.

---

## Core Components

### 1. Create Client

```python
import os
import anthropic

client = anthropic.Anthropic(
    api_key=os.getenv("ANTHROPIC_API_KEY")
)
```

### Why this matters
- This is the connection to the Anthropic API.
- The SDK sits on top of the same model infrastructure but adds orchestration primitives.

### Key architect insight
- Without a valid client, no session or agent can be created.
- A client is the “gateway” into the SDK runtime.

---

### 2. Create Agent

```python
agent = client.beta.agents.create(
    name="Support Agent",
    description="Handles customer support",
    model="claude-opus-5-5",
    system="You are a helpful assistant.",
    tools=[...]
)
```

### Why this matters
- The agent is the model configuration + persona + capabilities bundle.
- It defines:
  - model
  - system instructions
  - available tools
  - task-specific behavior

### Key architect insight
- In the Messages API, you manually craft `messages`, `tools`, and `system`.
- In the Agent SDK, those are packaged into an agent object.

---

### 3. Create Environment

```python
environment = client.beta.environments.create(
    name="demo-env",
    config={
        "type": "cloud"
    }
)
```

### Why this matters
- Environments hold the runtime context in which the session executes.
- They provide a managed execution environment for agent workflows.

### Key architect insight
- The session is not isolated from the environment; it runs inside it.
- This is especially important in long-running or multi-tool workflows.

---

### 4. Create Session

```python
session = client.beta.sessions.create(
    agent={
        "type": "agent",
        "id": agent.id,
        "version": agent.version
    },
    environment_id=environment.id
)
```

### Why this matters
- A session is the conversational runtime for a given agent.
- It preserves state across events and turns.

### Key architect insight
- In the Messages API, the architect manages the state.
- In the Agent SDK, Anthropic manages session state internally.

---

### 5. Send User Message

```python
client.beta.sessions.events.send(
    session_id=session.id,
    events=[
        {
            "type": "user.message",
            "content": [
                {
                    "type": "text",
                    "text": "Check order ORD-1001"
                }
            ]
        }
    ]
)
```

### Why this matters
- This is how the user request enters the session.
- Messages are represented as events, not as raw JSON arrays like the Messages API.

### Key architect insight
- The agent SDK event model is more structured and lifecycle-driven.
- It exposes a richer orchestration experience for tool calls, pauses, and completion.

---

### 6. Stream Events

```python
with client.beta.sessions.events.stream(
    session_id=session.id
) as stream:

    for event in stream:
        print(event.type)
```

### Why this matters
- The SDK streams events instead of waiting for a final single response.
- This is ideal for agentic systems where multiple behaviors happen over time.

### Key architect insight
- Event streaming enables:
  - reasoning observation
  - tool request detection
  - state updates
  - long-running workflow management

## Important Event Types

### `agent.message`

Claude emits text.

```python
if event.type == "agent.message":
    print(event.content)
```

Example:

```text
Order located.
Refund requires escalation.
```

### Why this matters
- This is the standard generated text response.
- It represents agent output during the session.

### Key architect insight
- Text output is not necessarily final.
- Claude may continue with tool use or pause before finishing.

---

### `agent.custom_tool_use`

Claude wants your application to execute a custom tool.

```python
if event.type == "agent.custom_tool_use":
    print(event.name)
    print(event.input)
```

Example:

```text
lookup_order
{
  "order_id": "ORD-1001"
}
```

### Why this matters
- This is the Agent SDK equivalent of `tool_use` from the Messages API.
- It signals a required external action.

### Key architect insight
- The model is not executing the tool itself.
- Your app must run the function and return the result back to the session.

---

### `session.status_idle`

Session is waiting or completed.

```python
if event.type == "session.status_idle":
    print(event.stop_reason.type)
```

### Why this matters
- The session is in a stable state.
- The architect can inspect why the session paused or ended.

### Key architect insight
- `session.status_idle` usually means the agent is not currently active.
- It is often a checkpoint before the next action or finalization.

---

### `session.status_terminated`

Session ended permanently.

```python
if event.type == "session.status_terminated":
    print("Done")
```

### Why this matters
- This indicates the session lifecycle is complete.
- No more events should be expected unless a new session starts.

### Key architect insight
- `session.status_terminated` is a clean end-of-workflow signal.
- Use it as a terminal condition for orchestration logic.

## Custom Tool Flow

### Tool Definition

```python
{
  "type": "custom",
  "name": "lookup_order",
  "description": "Retrieve order details",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string"
      }
    },
    "required": ["order_id"]
  }
}
```

### Why this matters
- This declares the external capability the model can use.
- It must follow a strict schema so Claude can reason about the arguments correctly.

### Key architect insight
- Tool validation is non-negotiable.
- Bad schema = bad invocation = broken workflow.

---

### Execute Tool

```python
result = execute_custom_tool(
    event.name,
    event.input
)
```

### Why this matters
- This is where your app connects the external system or business logic.
- The model never directly executes the tool; your runtime does.

---

### Return Result

```python
client.beta.sessions.events.send(
    session_id=session.id,
    events=[
        {
            "type": "user.custom_tool_result",
            "custom_tool_use_id": event.id,
            "content": [
                {
                    "type": "text",
                    "text": result
                }
            ]
        }
    ]
)
```

### Why this matters
- This is the Agent SDK equivalent of injecting a `tool_result` back into the message history.
- It ensures Claude sees the result and can continue reasoning.

### Key architect insight
- Tool execution alone is not enough.
- The result must be returned to the session as structured feedback.

## Stop Reasons Cheat Sheet

## `end_turn`

### What is `end_turn`?
- **Definition:** Claude has completed the task and produced its final answer.
- **Role:** Safe termination of the session.
- **Architect’s Responsibility:**  
  - detect final answer
  - present result to the user
  - stop the workflow

### Workflow with `end_turn`

```text
User
 ↓
Claude
 ↓
Answer Generated
 ↓
end_turn
```

### Example

```python
event.stop_reason.type == "end_turn"
```

### Key architect insight
- This is the normal successful completion signal.
- It is the Agent SDK equivalent of “the task is done.”

### Common exam trap
- Confusing `end_turn` with a tool request.
- `end_turn` means completion, not tool execution.

---

## `requires_action`

### What is `requires_action`?
- **Definition:** Claude needs the application to execute a tool before it can continue.
- **Role:** Equivalent to `tool_use` in the Messages API.
- **Architect’s Responsibility:**  
  - detect `requires_action`
  - run the tool
  - return the result to the session

### Workflow with `requires_action`

```text
Claude
 ↓
Tool Request
 ↓
requires_action
 ↓
Application Executes Tool
```

### Example

```python
event.stop_reason.type == "requires_action"
```

### Why this matters
- This is the most common Agent SDK stop reason.
- It signals that the agent is not done, but is waiting on external system execution.

### Key architect insight
- In the SDK, this is the orchestrator’s explicit cue to act.
- The loop is not complete until the tool result is sent back.

### Common exam trap
- Treating `requires_action` as the final result.
- It is not completion; it is a continuation trigger.

---

## `max_tokens`

### What is `max_tokens`?
- **Definition:** Claude reached the token output ceiling for the response.
- **Role:** Indicates truncated or incomplete output.
- **Architect’s Responsibility:**  
  - continue from where the output stopped
  - summarize history
  - raise the token budget if appropriate
  - split the task into chunks

### Example

```python
event.stop_reason.type == "max_tokens"
```

### Recovery approach

```python
Continue from where you stopped.
```

### Key architect insight
- This is not a refusal.
- It is a token-budget limit.
- In long workflows, summarization often becomes necessary.

### Common exam trap
- Confusing `max_tokens` with context-window overflow.
- `max_tokens` is output cap.
- `model_context_window_exceeded` is total context overflow.

---

## `pause_turn`

### What is `pause_turn`?
- **Definition:** The agent intentionally pauses before continuing.
- **Role:** Enables multi-step or long-running workflows to resume later.
- **Architect’s Responsibility:**  
  - continue without adding a new user prompt
  - preserve current session state
  - resume from the same point in the loop

### Workflow with `pause_turn`

```text
Research Phase
 ↓
Pause
 ↓
Resume Later
```

### Example

```python
event.stop_reason.type == "pause_turn"
```

### Key architect insight
- This is a deliberate halting mechanism.
- It is especially useful when the agent needs to wait for more context or a controlled continuation.

### Common exam trap
- Sending new user input when resuming.
- The safer pattern is to continue from the same context.

---

## `stop_sequence`

### What is `stop_sequence`?
- **Definition:** Claude detected a custom stop marker configured by the architect.
- **Role:** Provides deterministic completion for structured output.
- **Architect’s Responsibility:**  
  - define a unique stop marker
  - parse it cleanly
  - end the session when it appears

### Example

```python
event.stop_reason.type == "stop_sequence"
```

### Example prompt pattern

```python
stop_sequences=["END"]
```

Output:

```text
Task completed
END
```

### Key architect insight
- This is the SDK equivalent of a custom boundary condition.
- It gives the architect “hard stop” control without waiting for the model to decide naturally.

### Common exam trap
- Confusing `stop_sequence` with `end_turn`.
- `end_turn` is natural completion.
- `stop_sequence` is explicit custom termination.

---

## `refusal`

### What is `refusal`?
- **Definition:** Claude refused to continue because the request violates safety or policy.
- **Role:** Protects against unsafe or disallowed content.
- **Architect’s Responsibility:**  
  - inspect the reason
  - stop cleanly
  - optionally reframe the task safely

### Example

```python
event.stop_reason.type == "refusal"
```

Example output:

```text
Request violates safety policy.
```

### Key architect insight
- This is not a bug or a tool issue.
- It is a compliance/security layer.
- You must handle it explicitly in governance-heavy workflows.

### Common exam trap
- Assuming refusal can always be overridden.
- In reality, you may need to reframe the request or remove unsafe content.

---

## `model_context_window_exceeded`

### What is `model_context_window_exceeded`?
- **Definition:** The total input size exceeds the model’s context limit.
- **Role:** Indicates memory overflow in the request.
- **Architect’s Responsibility:**  
  - summarize earlier content
  - trim history
  - chunk documents
  - make retrieval narrower
  - reduce unnecessary prompt payload

### Example

```text
History
+
Tool Results
+
Documents
+
Prompt
----------------
> Context Window
```

### Key architect insight
- This is different from `max_tokens`.
- `max_tokens` = output cap
- `model_context_window_exceeded` = too much input/context

### Common fix patterns
- Summarize old messages
- Remove redundant history
- Chunk large files
- Use RAG instead of full-document ingestion
- Keep only relevant tool results

## Error Isolation Pattern

### Problem
Multiple tools requested at once, but not all succeed.

```text
Tool A ✅
Tool B ❌
```

### Wrong approach

```text
Restart entire workflow
```

### Correct approach

Return both results, including the failure.

```python
{
  "tool_use_id": "tool_1",
  "result": "success"
}

{
  "tool_use_id": "tool_2",
  "is_error": True,
  "content": "timeout"
}
```

Then Claude adapts:

```text
Tool A succeeded.
Tool B failed.
Retrying Tool B.
```

### Why this matters
- In real systems, partial success is common.
- Architects need resilient orchestration, not all-or-nothing loops.

### Key architect insight
- Error isolation keeps the workflow alive.
- The system can learn from partial success and continue intelligently.

## Context Window Pattern

### Bad pattern

```python
messages.append(all_previous_history)
```

This causes token growth forever.

### Good pattern

```python
summary = """
Customer verified
KYC complete
Fraud check passed
"""

messages = [
    {
        "role": "system",
        "content": summary
    }
]
```

### Why this matters
- Context window usage grows with history, tool results, documents, and prompt length.
- Long-running workflows need summarization, not indefinite accumulation.

### Key architect insight
- The architect should not “keep everything forever.”
- Older content should be compressed or replaced with concise fact summaries.

## Agent SDK vs Messages API

| Feature | Messages API | Agent SDK |
|---|---|---|
| Conversation State | You manage manually | Anthropic manages in session |
| Tool Loop | You implement | Agent handles orchestration |
| Sessions | No session concept | Yes |
| Environments | No environment concept | Yes |
| Event Streaming | Limited | Rich event system |
| Custom Tools | Yes | Yes |
| Long-running workflows | Manual | Native |
| Stop reason for tools | `tool_use` | `requires_action` |

### Key architect insight
- The Agent SDK is better for orchestration-heavy systems.
- The Messages API is more transparent and lower-level.
- Both are valid, but the SDK simplifies high-level workflows.

## Final Takeaways

### The Agent SDK is the orchestration engine
It gives the architect:
- a session model
- event-driven reasoning
- structured tool execution
- built-in lifecycle states
- better management of complex multi-step workflows

### The key loop is:
- user sends input
- agent reasons
- agent emits event
- if `requires_action`, execute tool
- return tool result
- continue until `end_turn`, `stop_sequence`, or a safety condition

### The key architectural rule
- Never let the workflow run without explicit stop conditions.
- Always handle:
  - tool execution
  - result injection
  - context-window risk
  - failure isolation
  - safe termination

---

## Exam Summary

The Agent SDK is the higher-level companion to the Messages API. It abstracts the orchestration logic and gives you a cleaner lifecycle:

- create agent
- create environment
- create session
- send user message
- stream events
- handle tool requests
- inject results
- terminate when done

This is the key difference between “raw API usage” and “agentic orchestration.”
